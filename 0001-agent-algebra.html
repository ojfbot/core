An algebra for agents

Lesson 0001 · agent-algebra-dynamic-workflows · for choosing operators, not describing features

Boris Cherny says three things in a row that are more connected than they look: that dynamic workflows haven't really been written about much, that his background is functional programming, and that the design is essentially an algebra for agents. (transcript) The third is a consequence of the second, and the first is why you have to work it out yourself.

An algebra is a set of things plus operations that combine them and give you back the same kind of thing. Numbers with +. Here: agents, with sequence and parallel. The payoff of calling it an algebra is composition — a combination of agents is itself an agent-shaped thing, so it can be combined again. That is what lets one prompt become a staged fan-out: agents do a first pass, another set verifies or summarises, a third stage fans out again. (transcript)

The operator the transcript doesn't settle

Boris names both operators and doesn't say which to reach for. The runtime does, and it is emphatic: default to the sequential-composition operator. To see why, you have to notice something the word "sequence" hides.

OperatorBehaviourWall-clock
parallel(...)a barrier — awaits every branch before returningthe slowest branch, per stage
pipeline(items, s1, s2)no barrier — each item flows through all stages independentlythe slowest single item's whole chain

So pipeline is not "the slow one." Item A can be in stage 3 while item B is still in stage 1. A barrier, by contrast, makes every fast branch sit and wait for the slowest one at every stage. If five finders run and the slowest takes three times the fastest, a barrier throws away two thirds of the fast finders' time — and it does that again at each stage boundary.

This is the same reason a build system prefers a dependency graph over phases. Phases are easier to reason about and they idle everything that could have run ahead.

Which makes the real question sharp: a barrier is correct only when stage N needs cross-item context from all of stage N−1. Deduplicating across a full result set before expensive downstream work. Early-exit when the total count is zero. A prompt that says "compare against the other findings." Those genuinely need everyone to arrive.

And the tempting wrong reason, worth naming because it feels like a reason: "I need to flatten or filter the results first." That is not a barrier — a transform with no cross-item dependency belongs inside a stage. If you find yourself writing collect → transform → collect, and the middle step never looks across items, the barrier bought you nothing and cost you the idle time.

Why the runtime forbids the clock

Here is where "my background is functional programming" stops being biography.

In the workflow runtime, Date.now(), Math.random(), and an argless new Date() throw. Not deprecated, not discouraged — they raise. A first reading says sandbox limitation. That reading is wrong, and the right one is the whole design.

A workflow run is journalled. When you resume it, the longest unchanged prefix of agent calls returns cached results instantly, and only the first edited call onward re-runs. Same script, same arguments, and every prior result is reused.

That guarantee only holds if the script is a pure function of its inputs — if running it twice with the same arguments describes the same work. A clock read breaks that. So does a random draw. One Date.now() in a branch condition and the replayed run may take a different path than the journal recorded, and the cache is quietly wrong rather than loudly broken.

So the prohibition is the feature. Referential transparency isn't decoration borrowed from an FP background; it is the precondition for cheap resume, and the runtime enforces it by refusing the impure calls outright. Timestamps come in through arguments or get stamped after the run — pushed to the edges, exactly as an FP practitioner would push effects to the edges.

1. You fan out five reviewers, then verify each finding. Reviewers finish at very different speeds. Which composition, and why?

Pipeline — verification doesn't need the other reviews. Verifying finding X requires X, not the full set, so there is no cross-item dependency and the barrier only buys idle time. "Conceptually separate" is the trap: separate stages are exactly what a pipeline models, and separate ≠ synchronised. Token count is unchanged either way — the same agents run; only wall-clock differs.

2. Now the second stage must drop duplicate findings across all reviewers before any expensive verification runs. What changes?

This is the case a barrier is for. Deduplicating across the full set is a real cross-item dependency — you cannot know X is a duplicate until you have seen everything. Note how narrow that made it: the operator changed because the data dependency changed, not because the pipeline felt untidy. That is the whole decision rule.

3. Why does the runtime raise on Date.now() instead of simply allowing it?

Resume depends on purity. A resumed run reuses the longest unchanged prefix of agent calls, which is only sound if the same script and arguments describe the same work. An impure read can send the replay down a different path than the journal recorded — and the failure is silent, which is why it is refused at the call rather than warned about. Effects get pushed to the edges: pass timestamps in as arguments, or stamp results after the run returns.

The other half: loops and routines

Dynamic workflows are one task decomposed. Loops and routines are the opposite shape — one repetitive task that doesn't share context between runs, though it may share memory. A loop runs locally; a routine runs in the cloud, so the laptop can close. (transcript)

The example worth sitting with is that Anthropic points these at their own codebases: dead-code removal, shipping fully-rolled-out experiments, writing missing tests, deleting useless ones, and an "abstraction police" that finds near-duplicate abstractions and unifies them. Boris notes the dead-code routine is a single sentence and that they never prompted the static-and-dynamic-analysis approach — it worked that out. (transcript)

Two claims are doing different work there, and it is worth keeping them apart: the mechanism is simple is demonstrated, while it does the work of dozens or hundreds of engineers is an unmeasured estimate — the transcript hedges its own agent counts a few lines earlier.
