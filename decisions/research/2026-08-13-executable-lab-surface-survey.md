# Research — executable-lab surface survey (cca-prep workbench)

**Date:** 2026-08-13 · **Ticket:** wayfinder #457 (map cca-prep-workbench) · **Method:** deep-research harness, ONE cycle (5 angles, 144 claims, 15 adversarially verified, 6 refuted) · **Feeds:** #459 (lab-surface selection) · **Gated by:** #456 (zero-dependency rule)

## Verdict (one paragraph)

Five mechanisms were surveyed for an executable lab surface inside cca-prep: in-browser WASM Python (JupyterLite/Pyodide), an in-page code-cell strip (CodeMirror or CodeJar + a sandboxed Worker + AST grading), no engine at all (a terminal-side runnable template driven by `uv`/`node --test` with a machine-readable report), static HTML pages with copy-run blocks and non-executing self-check, and third-party hosted embeds (StackBlitz/WebContainers, CodeSandbox, Replit, Codespaces). The cycle established that every in-browser-execution option puts the operator's API key in client-side code and depends on an Anthropic CORS header that has no first-party prose documentation; that the Batches API — one of the six required lab topics — is measurably CORS-blocked at `/v1/messages/batches` from every origin tested, so no in-browser mechanism can teach it against the live API; that both official Anthropic SDKs honour a `base_url`/`baseURL` override and were measured accepting a fake key against a 12-line `node:http` mock, making key-free offline labs achievable on the stack cca-prep already has; and that the host itself imposes two concrete costs the ticket brief did not carry — `engine/server.mjs` has no generic static-file handler (one hardcoded HTML route, no MIME map), and neither `scripts/ui-gate.sh` nor any other CI step detects a `package.json`, lockfile, or `node_modules` anywhere in the tree, so the zero-dependency rule is enforced by CLAUDE.md prose rather than by machinery in either world of #456. Three hosted-embed options carry non-technical blockers (StackBlitz embedding is restricted to paying customers at 500 sessions/month; Replit editable embeds were deprecated to read-only; Codespaces requires a GitHub account and network). The evidence on whether in-place execution actually teaches better than copy-run is thin in both directions: the single closest head-to-head favours interactive content but is vendor-authored and confounded by an 86% time-on-task difference, while Parsons-problem research found a non-executing check matched execution-based practice on learning and retention in less time. #459 decides; this document names no winner.

## Verified findings

**Host constraints (all read on disk 2026-08-13, working tree clean at HEAD)**

1. `engine/server.mjs` serves HTML from exactly one route — `/` or `/index.html` at lines 159-160 — with no generic static-file handler, no MIME map, and no directory serving. Live-probed on port 8799: `GET /lab.html`, `/public/index.html`, `/app.css`, and `/index.html/` all return 404 `{"error":"not found"}`. **Corrected by verification:** the original framing ("any new lab page requires adding a route") is true only for a page at a *new path*; `engine/public/index.html` is fully self-contained (27,014 bytes, zero `script src` / `link rel` / external hrefs), so a lab embedded as another view inside it requires no server change at all. Two different cost profiles. Source: `cca-prep/engine/server.mjs`.

2. The API route regex at `server.mjs:174` is `^\/api\/([a-z0-9-]+)\/([a-z]+)$` — the *action* segment accepts lowercase letters only, no digits, no hyphens. Probed live: `/api/ccar-f/lab` reaches the dispatcher; `/api/ccar-f/lab-run` 404s at the regex. A lab-result endpoint must be a single lowercase word or the regex changes too. `POST /api/<exam>/lab-result` would **not** be in-pattern as written. Source: same file (the original claim that such an endpoint "would be in-pattern" is amended by this).

3. `server.mjs` emits no CORS headers and has no OPTIONS handling; an OPTIONS request to `/api/*` matches the route match but no method branch and falls through to the line-232 catch-all 404. Consequence: a lab page opened via `file://` could not call this server's API. (Source-read inference; OPTIONS not separately probed.)

4. `scripts/ui-gate.sh` line 7 is a single `grep -rniE --exclude=ui-gate.sh "from ['\"]react|import React|@carbon/|carbon-components" engine/ scripts/`. Anything outside those two directories passes unconditionally — verified by placing a file containing `import React from "https://esm.sh/react@18"` in a sibling `labs/` dir and watching the gate pass. Source: `cca-prep/scripts/ui-gate.sh` (last touched f678d08, 2026-08-11).

5. **Corrected by verification:** the gate does *not* "match import syntax, not network fetches". Two of its four alternatives (`@carbon/`, `carbon-components`) are bare substrings with no anchoring. Measured inside `engine/`: a `<script src="https://cdn.jsdelivr.net/npm/@carbon/web-components@2/…">` tag FAILS the gate; the prose sentence `This lab intentionally avoids carbon-components styling.` FAILS the gate; `import React from "https://esm.sh/react@18"` FAILS the gate. The `-i` flag with no word boundaries also means `import ReactiveExercise from "./x.js"` is a false positive. The only CDN case that passes is React loaded as a UMD `<script src>` (verified: unpkg's `react.production.min.js` contains neither matching string).

6. `.github/workflows/ci.yml` runs exactly three steps after checkout + `setup-node@v4` (node 24): `node --test`, `node scripts/boundary-check.mjs`, `bash scripts/ui-gate.sh`, with an explicit "Zero-dependency repo: no install step" comment. There is **no** check anywhere in CI for `node_modules`, `package.json`, or a lockfile; `security-scan.yml` sets `skip-dependency-audit: true` because there is no lockfile, so a newly introduced lockfile would not be audited either. A sidecar lab directory with real npm dependencies passes the entire CI suite today. The zero-dep rule is enforced by CLAUDE.md prose, not by machinery. Sources: `.github/workflows/ci.yml`, `scripts/ui-gate.sh`, `scripts/boundary-check.mjs`.

7. `engine/public/index.html` is **490 lines**, not the 446 stated in the ticket brief; `engine/server.mjs` is 239 lines. Confirmed independently by two angles. Source: `wc -l` on disk.

8. Repo scale for weighing any vendored binary: 162 tracked files totalling 666,008 bytes; `.git` is 3.1 MB; the largest tracked file is `decks/ccar-f/bank-mock1.json` at 62,482 B. Pyodide-core compressed (6,757,798 B) is 10.1x the entire tracked worktree; the unpacked minimal browser runtime (13,522,819 B) is ~20x it and ~4.4x the whole `.git` history. Source: local measurement 2026-08-13.

9. `publication-checklist.md` documents an unresolved operator-only git-history purge blocking the public flip, and records that GitHub retains PR head refs (`refs/pull/N/head`) server-side so purged commits stay fetchable without a Support ticket. Any binary committed before the flip is effectively permanent. Source: `cca-prep/publication-checklist.md`.

**Anthropic API reachability from a browser**

10. A cross-origin POST to `https://api.anthropic.com/v1/messages` carrying `anthropic-dangerous-direct-browser-access` passes CORS and returns a readable 401 body; without the header it is blocked at preflight. Independently reproduced three ways: via curl against the live API (OPTIONS with the header → HTTP 200, `access-control-allow-origin: *`; without → HTTP 400 body `Disallowed CORS origin`, no ACAO), via Playwright in Chrome 151 (5/5 reproductions, including inside a Web Worker), and inside a real Pyodide runtime. Sources: live measurement 2026-08-13; https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access/ (third-party).

11. **Corrected by verification:** the negative-control error string is `TypeError: Failed to fetch`, **not** `AbortError: Failed to fetch`. That combination is not one Chromium emits — CORS rejection is spec'd to reject with `TypeError`; `AbortError` comes from AbortController with the message "The user aborted a request." Using "AbortError" as the diagnostic signature for "CORS blocked" would mis-classify real timeouts. 5/5 reproductions gave `TypeError`.

12. **Corrected by verification:** the header gates on *presence*, not value — sending it with the literal value `"false"` still passes CORS (401, response type `cors`, ACAO `*`). Every write-up says `: true`. Undocumented either way; should not be relied on.

13. **Corrected by verification:** the header is not the sole gate. The TypeScript SDK throws client-side *before* any request if `!options.dangerouslyAllowBrowser && isRunningInBrowser()` (`src/client.ts:548`), so setting the header via `defaultHeaders` does not help — the constructor throws first. The Python SDK — the relevant one under Pyodide — has **zero** browser handling: greps of `_client.py`/`_base_client.py`/`_constants.py` for `browser|cors|dangerous` return no hits, and a grep of the anthropic 0.122.0 wheel for `dangerous-direct-browser` returns nothing. Its default headers are just `anthropic-version: 2023-06-01` (`_client.py:373`).

14. **Load-bearing for #459 — the Batches API is CORS-blocked.** Measured, stable across 3 runs and 5 origins (`http://localhost:8631`, `https://jupyterlite.github.io`, `http://localhost:8888`, `null`, `https://example.com`): `OPTIONS /v1/messages/batches` with the dangerous header returns HTTP 400, body `Disallowed CORS origin`, no ACAO; `GET /v1/messages/batches` returns 401 with no ACAO (body unreadable in a browser). Per-endpoint map: `/v1/messages`, `/v1/models`, `/v1/messages/count_tokens` are CORS-enabled; `/v1/messages/batches` and `/v1/organizations/me` are blocked. A nonexistent path (`/v1/zzz-nope`) preflights 200, so batches is on an explicit deny path, not merely unrouted. Endpoint-scoped, not origin-scoped — a localhost allowlist is not a workaround. Consequence: an in-browser lab can teach five of the six required topics natively; the Batches topic needs a mock, a fixture, or a local proxy. Empirical only; no first-party documentation of per-endpoint CORS policy was found, so this could change without notice.

15. Streaming does pass CORS: `POST /v1/messages` with `"stream":true` plus the header returns ACAO `*` and `access-control-expose-headers: *`.

16. A second-order CORS trap: the preflight returns `access-control-allow-credentials: true` alongside `access-control-allow-origin: *`. Per spec a browser rejects that combination when credentials mode is `include`. `pyfetch` inherits fetch's `same-origin` default so it works, but any lab scaffold setting `credentials:'include'` breaks with a confusing error.

17. Anthropic's TypeScript SDK docs state browsers are "disabled by default to avoid exposing your secret API credentials" and name only internal tools and development/debugging as acceptable. The raw header itself has **no** first-party prose documentation anywhere found — the only first-party artifact naming it is SDK source (`client.ts:1504`). Note `docs.anthropic.com` now 301-redirects to `platform.claude.com`. Source: https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/typescript.

**In-browser Python (Pyodide / JupyterLite)**

18. Under Pyodide 314.0.4 (CPython 3.14.2, `sys.platform` `emscripten`), `%pip install anthropic` succeeds and resolves anthropic 0.122.0. Confirmed independently. Note anthropic 0.122.0's PyPI upload time is 2026-08-13T18:36:01Z — it did not exist on 2026-08-12, the survey's stated verification date.

19. **Corrected by verification:** the claimed 401 from a stock client is **not reachable**. A default `anthropic.Anthropic(api_key=…)` under Pyodide raises `anthropic.APIConnectionError: Connection error.` (both sync and async) because the CORS preflight fails; the SDK's retry loop swallows it. The genuine 401 appears only with `default_headers={"anthropic-dangerous-direct-browser-access": "true"}`. Decision-relevant consequence: a Pyodide lab cannot run copy-pasted stock SDK code — the scaffold must inject a non-default header, so lab code diverges from the idiomatic code the exams test.

20. **Corrected by verification:** "the official SDK's httpx transport works under Pyodide" is true but not because upstream httpx is compatible. Pyodide ships a **fork** — pyodide-recipes `packages/httpx/meta.yaml` pins `https://github.com/hoodmane/httpx/archive/refs/tags/pyodide_release_5.zip` with the comment "Until the PR for emscripten support gets merged, build it from the PR source". Upstream httpcore has zero `emscripten` hits. micropip resolves httpx from the Pyodide lockfile, so the version string `0.28.1` makes the fork invisible. Pyodide's own `test_httpx.py` gates every *synchronous* test with `@requires_jspi`. The working transport is guaranteed only inside Pyodide's own package set.

21. **Documentation-vs-reality discrepancy:** JupyterLite's kernels doc still says the Pyodide kernel "Does not support sleeping with `from time import sleep`", but measured `time.sleep(1.0)` returned after 1.01 s and `await asyncio.sleep(1.0)` after 1.00 s — on a page that is *not* cross-origin isolated (`crossOriginIsolated === false`, `SharedArrayBuffer` undefined). Blocking submit/poll loops work today; the doc is stale. Source: https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html + measurement.

22. Pyodide's documented network sandbox: no raw sockets, CORS restrictions, no synchronous networking on the main thread, HTTP/HTTPS only. `ssl` is "replaced with a stub implementation that does not use OpenSSL". urllib3 has supported Emscripten since 2.2.0 (auto-enabled when `sys.platform == 'emscripten'`), so Requests works, but proxies, TLS/certificate customisation, and low-level socket options are documented unsupported; response streaming requires a Web Worker *and* cross-origin isolation. Sources: https://pyodide.org/en/stable/usage/api/python-api/http.html, https://urllib3.readthedocs.io/en/stable/reference/contrib/emscripten.html.

23. Version coupling is strict: `jupyterlite-pyodide-kernel >=0.8.0,<=0.9.0` pins Pyodide 314.*, Python 3.14.*, Emscripten 5.0.3, with the docs noting "the Emscripten version is strict down to the patch version". Current: `jupyterlite-core` 0.8.1 (2026-07-08), `jupyterlite-pyodide-kernel` 0.8.3 (2026-08-11).

24. Kernels run in a Web Worker, so "it is not possible to directly manipulate the DOM from inside a worker" — two-way integration between a lab cell and the drill UI needs postMessage plumbing, not direct DOM access. Docs limit support to "the latest Chrome and Firefox versions"; Service Workers do not work in Firefox private windows, and a failed registration produces `FileNotFoundError: [Errno 44] No such file or directory` (jupyterlite#1371). Safari status not stated.

25. Host-page embedding is a first-class documented feature: the REPL is an `<iframe>` configured purely by URL params — `kernel=python`, `code=<urlencoded>` (auto-executes on load, confirmed by measurement), `execute=0` (prefill without running), `hideCodeInput=1`, `clearCellsOnExecute=1`. Full notebooks are pre-seeded at build time via `--contents`. Source: https://jupyterlite.readthedocs.io/en/stable/quickstart/embed-repl.html.

26. Learner state persists to IndexedDB and "a user's locally-modified copy will take precedence over any server contents, even if the server contents are newer"; all contents on the same domain are shared across JupyterLite instances unless `contentsStorageName` is changed. Reset is the irreversible "Clear Browser Data" command. Source: https://jupyterlite.readthedocs.io/en/stable/howto/content/files.html.

27. Licensing is permissive: Pyodide is MPL-2.0 (file-level copyleft — vendoring unmodified artifacts triggers no disclosure obligation, modifying Pyodide sources would), JupyterLite is BSD 3-Clause.

28. **Corrected by verification:** Pyodide sizes and versions in the raw cycle were partly stale. Current (314.0.4, published 2026-08-04, measured 2026-08-13): `pyodide.asm.wasm` 9,596,386 B raw / 3,435,435 B brotli on-wire; `python_stdlib.zip` 2,545,198 B; `pyodide.asm.mjs` 1,249,500 B — and note `pyodide.asm.js` from v0.28.3 is now a 404, replaced by the `.mjs`. Minimal browser payload: 13,522,819 B raw / 6,233,935 B brotli. The full distribution tarball (414,666,750 B = 395.5 MiB) is **3.95x over GitHub's 100 MiB per-file block** — it cannot be committed to git at all, contradicting the "far below GitHub's hard caps" framing; only pyodide-core (6,757,798 B) clears the caps comfortably.

29. The sibling repo's Jupyter install does **not** transfer: `newline-ai-course` has a server-side CPython JupyterLab (`.venv` 520 MB against a 1.0 GB repo dir, 100+ pinned packages, `.venv/` gitignored). JupyterLite shares the notebook file format and front-end UX but none of the runtime, kernel, or package-installation path. Its root `requirements.txt` contains no LLM SDK; only `resume-builder/requirements.txt` pins `anthropic>=0.39`.

**In-page editor + sandbox + grading**

30. A single self-hosted pre-bundled ESM file works with no bundler, no import map, and no `node_modules` — independently reproduced from scratch. esm.sh's `codemirror@6.0.2` standalone bundle is 377,547 bytes (SHA-256 `a485c133…`), contains zero `import` statements and zero dynamic imports, injects its own CSS via StyleModule (no stylesheet link), and mounted a working `basicSetup` editor with 4 gutter elements rendering, zero console errors, and exactly two HTTP requests (`GET /`, `GET /codemirror.mjs`) from a hand-written 8-line `node:http` server. **Corrected:** gzip is ~121,376 B headerless (the cited 121,382 implies a 5-char stored filename); Brotli q11 is 104,111 B.

31. **Corrected by verification — the single-file property does not survive adding a language mode.** `basicSetup` ships no parser: measured `.cm-content .cm-line span` = 0 token spans, line 1 innerHTML is literal `const x = 1;`. 377 KB buys a text editor with **zero syntax highlighting**. `@codemirror/lang-javascript@6.2.5` is +359,242 B and `@codemirror/lang-python@6.2.1` is +314,353 B, and **both contain `import __Process$ from "/node/process.mjs"`** — an esm.sh absolute path that 404s on a self-hosted server. Self-hosting them requires vendoring the unenv shim and rewriting the specifier, or adding the import map the claim says isn't needed.

32. **Corrected by verification — CodeMirror's own bundle-size figures are four years stale.** The page's numbers were added 2022-06-07 and never revised; the page carries no version stamp or date. Reproducing the docs' own Rollup+Terser recipe today at codemirror 6.0.2 / lang-javascript 6.2.5 / view 6.43.8: basicSetup + a language mode is **1,257,829 B raw / 498,849 B minified / 163,276 B gzip / 138,532 B brotli** (docs say 1 MB / 400 kB / 135 kB — understated by 21–26%); minimalSetup is **819,455 B / 280,511 B / 89,750 B / 77,958 B** (docs say 700 kB / 250 kB / 75 kB — understated 12–20%). Use the measured figures.

33. **Corrected by verification — "first-party guidance assumes a bundler" is version-stale.** The quotes are verbatim but the claim silently drops the author's hedges "at the time of writing" and "for the time being". Git archaeology on the canonical repo (moved from GitHub to `code.haverbeke.berlin`) dates that paragraph to **2021-01-05**, two months before Chrome shipped import maps; the page's recommended workaround, Snowpack, has had no release since 2021-08-26. Decisively: CodeMirror's own `/try` sandbox was switched to an import map on 2026-04-21 (commit 6ca502d) and is live — `https://codemirror.net/try/importmap.json` is 12,176 bytes, 161 entries, exactly one `@codemirror/state`, serving unbundled per-package ESM into a same-origin iframe. What survives: CodeMirror publishes no non-bundler guide and ships no UMD/browser-global build, so *some* npm→browser resolution step is still required — but it need not be a bundler. A minimal import map for `codemirror` + `@codemirror/lang-javascript` is 17 packages.

34. A Blob-URL Web Worker can have `globalThis.fetch` monkeypatched so learner code calling `fetch('https://api.anthropic.com/v1/messages')` never leaves the machine — verified capturing the exact request body `{"model":"claude-opus-5","tools":[{"name":"get_weather"}]}` and returning a canned response whose `stop_reason` (`tool_use`) the learner code read back. `Worker.terminate()` reliably kills `while(true){}` with the main thread responsive throughout.

35. That Worker is a **stability** boundary, not a security one: it inherits the page's origin, so learner code can still fetch same-origin URLs (including cca-prep's own `localhost:8631` endpoints) and reach same-origin storage. Only the DOM is unavailable. The real isolation boundary is `<iframe sandbox="allow-scripts">` *without* `allow-same-origin`: measured `location.origin === "null"`, `parent.document` unreadable, `document.cookie` throws, `localStorage` throws, `eval('1+1')` still returns 2, postMessage-only communication. MDN warns that combining `allow-scripts` with `allow-same-origin` on a same-origin document is "strongly discouraged" because the frame can remove its own sandbox attribute.

36. The iframe has a failure mode the Worker does not, though the evidence is thin: a sandboxed `srcdoc` iframe spinning infinitely starved the parent main thread (5 timer ticks instead of ~100 over a 1000 ms timer that took 1790 ms wall clock), and `ifr.remove()` returned in 0.1 ms but did **not** restore the parent (1 tick instead of ~50 over the next 500 ms). **Single measurement, one browser (Chromium 148 / Electron 42.7.0), same-site `srcdoc` frame sharing the parent's process.** A genuinely cross-origin sandboxed iframe would be site-isolated into its own process and may well not block the parent — untested. Do not generalise this.

37. `ShadowRealm` is not available: the TC39 proposal is at Stage 2.7; Stage 3 was requested at the December 2024 meeting without advancing.

38. AST-based grading is cheap and works: `acorn@8.18.0` bundled ESM is 121,565 B (34,158 gzip), zero runtime deps; measured import 5.6 ms, parse 11.50 ms, and a hand-written 6-line walk correctly detected a comparison against the literal `'tool_use'` in a BinaryExpression — i.e. you can assert on structure ("did they branch on stop_reason?") rather than on output.

39. Sucrase gotchas verified by breaking them: the esm.sh browser bundle is **not** self-contained (it imports a Node Buffer shim from `/node/buffer.mjs`, 28,845 B, and the page throws "Failed to fetch dynamically imported module" until it's vendored too); and `transforms:['typescript','imports']` emits CommonJS (`exports.__esModule`) rather than ESM, which will not run as a module.

40. Heavyweight editors are out of scale: `monaco-editor@0.56.0` npm unpacked is 97,911,464 B; `ace-builds@1.44.0` is 55,087,443 B.

**Terminal-side / no-engine mechanism**

41. `node --test` needs zero npm packages and ships built-in `spec`/`tap`/`dot`/`junit`/`lcov` reporters selectable with `--test-reporter=` and redirectable with `--test-reporter-destination=<file>`; `--watch` exists. Measured: a one-test file ran in 0.08 s wall and wrote valid JUnit XML. Node 24.11.1 also ran a `.ts` test file directly (1/1, 70.9 ms). Source: https://nodejs.org/api/test.html + local measurement.

The dependency-free alternatives are the line-oriented `tap` reporter or a custom `node:test` reporter module emitting JSON directly. pytest has a built-in `--junit-xml` but **no** built-in JSON reporter (JSON needs the third-party `pytest-json-report`).

43. Both official Anthropic SDKs honour a base-URL override, verified in source: Python reads `os.environ["ANTHROPIC_BASE_URL"]` with precedence kwarg > env > profile config (`_client.py:231-233`, `651-653`); TypeScript has `baseURL?: string` defaulting to `process.env['ANTHROPIC_BASE_URL']` (`client.ts:373-377`).

44. **Measured end-to-end:** a 12-line `node:http` server on :8632 returning a canned Messages response was consumed successfully by `anthropic.Anthropic(api_key="not-a-real-key", base_url="http://localhost:8632")` — the SDK parsed it and printed `stop_reason: tool_use` and `block type: tool_use | tool: get_weather {'city': 'Paris'}`. The SDK rejected neither the fake key nor the localhost host. Key-free, network-free labs are achievable on the exact stack cca-prep already uses.

45. Anthropic's own SDKs corroborate this pattern: `scripts/mock` in both `anthropic-sdk-python` and `anthropic-sdk-typescript` launches `npm exec --package=@stdy/cli@0.22.2 -- steady` on 127.0.0.1:4010 from the OpenAPI spec URL in `.stats.yml`, and CONTRIBUTING.md states "Most tests require you to set up a mock server against the OpenAPI spec". `tests/test_client.py` uses `base_url = os.environ.get("TEST_API_BASE_URL", "http://127.0.0.1:4010")` and `api_key = "my-anthropic-api-key"`.

46. The Anthropic OpenAPI spec is publicly downloadable without auth (1,812,294 bytes, OpenAPI 3.1.0, 89 paths) and covers the lab surface: `/v1/messages`, `/v1/messages/count_tokens`, and all Batches endpoints. Measured occurrences: `tool_use` 247, `stop_reason` 43, `input_schema` 23, `custom_id` 12, 549 `examples` keys. It declares exactly one server (`https://api.anthropic.com`) and **no sandbox/test host**.

The spec contains **zero** occurrences of `errorCategory` or `isRetryable` — the MCP structured-tool-error fields the labs must teach are not vendor-spec artifacts, so no spec-driven mock will emit them; those fixtures must be hand-authored. The spec does model the API error surface a retry-loop lab needs (`APIError`, `AuthenticationError`, `BetaGatewayTimeoutError`; `overloaded_error` ×11, `rate_limit_error` ×9, `invalid_request_error` ×11) but defines no `retry-after` or `request-id` headers.

Measured for a lab-shaped script: **23.73 s cold** (empty `UV_CACHE_DIR`, 21 packages, 70 MB cache), **2.22 s warm** (env materialised in 26 ms), **0.68 s warm + `--offline`**; empty cache + `--offline` is a hard failure. One online prime is mandatory; after that the loop is sub-second and fully offline. Single-trial numbers on one Mac and one network.

49. The operator's machine already has every runtime this angle needs: uv 0.10.7, Python 3.14.5, Node v24.11.1, pytest 9.0.2. (One-machine fact, not a general one.)

**Prior art for CLI exercise runners**

51. Exercism's `exercism test` runs a track-specific command from `workspace/test_configurations.go` with exactly three placeholders (`{{solution_files}}`, `{{test_files}}`, `{{slug}}`). Verified verbatim at both `main` and tag v3.5.8: python `python3 -m pytest -o markers=task {{test_files}}`, javascript `npm run test`, typescript `yarn test`, rust `cargo test --`, ruby `ruby {{test_files}}`. The struct also has a `WindowsCommand` field the claim omitted, and 77 `Command:` entries total. Material for #459: **there is no execution environment** — `cmd/test.go` splits the string on spaces (no shell, no quote handling), runs `exec.Command` in the CWD, and pipes stdout/stderr. No sandbox, no container, no toolchain provisioning. The runtime is the learner's laptop. It also only works inside a downloaded exercise directory, and hard-codes `npm`/`yarn` per track (a pnpm-only repo would be importing that assumption).

52. Exercism's Test Runner Interface is a file contract, verified against the upstream markdown (blob sha `e1f6075e`, last substantive commit 2025-09-30, current on `main`): the runner takes (slug, input dir, output dir), "must write a `results.json` file to the output directory", and "must exit with an exit code of 0 … regardless of the status of the tests". Budget verbatim: "100% CPU with 3GB of memory for a 20 second window per solution". **Corrected:** `tests` is *not* required at version 2+ unconditionally — the spec says "required if `status` = `fail` or `status` = `pass`", so a version-2 `error` result omits it; and `message` is required when status is `error` *or* when status is `fail` and version is 1 (capped at 65535 chars); and `test_code` is required only for Concept Exercises, SHOULD for Practice. The input dir is advisory-read-only, not enforced. Omitted per-test fields: `output` (must be limited to 500 chars) and `task_id`. Adjacent fact from the companion `docker.md`: Exercism's own harness runs test runners with `--network none`.

53. **Corrected by verification** — rustlings' state file is real but the described re-verification behaviour is wrong. Confirmed exactly, on both `main` and tag v6.5.0: `src/app_state.rs:26` is `const STATE_FILE_NAME: &str = ".rustlings-state.txt";`, and the format is documented in-source (header `DON'T EDIT THIS FILE!`, line 3 = current exercise, remaining lines = done exercises) — name-based, no timestamps, no attempt counts. But: the file lives in the *project root* (bare relative path opened from CWD), not the exercise directory; and bulk re-verification is **parallel and order-nondeterministic** (`thread::available_parallelism()`, fallback `DEFAULT_CHECK_PARALLELISM = 8`, work pulled off an `AtomicUsize`), checks **all** exercises not just completed ones, and is not part of the watch loop at all — it fires from `rustlings check-all`. The cited third-party page says nothing about ordering, so that clause had no source. Watch mode uses `notify` v8 on `exercises/` with a 200 ms debounce and only re-runs when the changed file *is* the current exercise. Adopting this pattern means a Rust toolchain + `cargo install` (this machine has no cargo), and its progress store would be a third persistence surface sitting on the wrong side of the telemetry boundary if placed in-repo.

54. **No established CLI exercise runner reports progress to a locally-running web UI.** Exercism submits to a remote website; rustlings and Python Koans keep state in local files with no web surface; NodeSchool's workshopper is terminal-only with a boolean `cb(ok)` verification callback. The nearest documented analog is Playwright's HTML reporter (writes a folder, served locally via `show-report`). The file-contract half is well-precedented; the local-web-UI hop is net-new integration code with no template to copy. This is absence-of-evidence, not proof of absence.

55. Prior art shows two verification granularities and the choice is consequential: PASS/FAIL-per-exercise (workshopper's boolean, rustlings' compile-and-run) versus per-assertion structured results (Exercism's `tests[]` with per-test name/status/message). Only the latter can drive a UI that says *which* judgment gap was missed.

56. Python Koans is the closest prior art to "fill the judgment gap in a working scaffold" — tests pre-written with a blank to fill (`self.assertEqual(__, 1+2)`), entry point a single stdlib script, exercise order a plain text file, watch mode an opt-in third-party add-on.

**Learning-efficacy evidence (thin in both directions)**

63. Edgcomb & Vahid (ASEE 2014) is the closest published head-to-head of copy-run against in-place execution: 136 CS1 students, static web content + a separate code-running tool vs interactive web-native content; post-lesson quiz 7.3 vs 8.6 correct (16% improvement for interactive, p = 0.016), lower-quartile students improving 64% more (p < 0.001). Three caveats belong with the number, all from the paper itself: participants spent **17.5 min with interactive vs 9.4 min with static+tool (p < 0.001)** — an 86% time-on-task difference the headline result does not control for; co-author Frank Vahid co-founded Zyante (later zyBooks, acquired by Wiley for $56M in 2019), the vendor of the winning condition; and the topic was C++ output statements taught to week-1 freshmen (72%), which transfers weakly to an experienced adult learning Anthropic API idioms.

64. The strongest counterweight: Ericson, Margulieux & Rick (Koli Calling 2017, DOI 10.1145/3141880.3141895) found that solving 2D Parsons problems with distractors took significantly less time than fixing code with errors or writing equivalent code, with **no statistically significant difference in learning performance or one-week retention** — i.e. a self-check requiring no code execution matched execution-based practice. A Parsons problem is checked by comparing block ordering: pure client-side array comparison, no interpreter, no sandbox, no network. Runestone Interactive is the existence proof that executing (ActiveCode) and non-executing (mixed-up code, fill-in-blank, clickable code) exercise types coexist in one statically-served HTML book.

65. Sentance, Waite & Kallia's PRIMM evaluation (493 experimental vs 180 control, 13 schools) found post-test M = 3.284 vs 2.575 with Mann-Whitney U = 36822.5, Z = -3.392, p = .001 — but **r = .13, a small effect**, quasi-experimental, students aged 11-14 learning Python basics, with the authors listing history/diffusion/instrumentation as validity threats. The "R" (Run) step means running provided code and observing output; it does not specify that the run happens inside the lesson page, so a copy-run workflow satisfies it.

66. `navigator.clipboard.writeText()` works on `http://localhost` with no library and no polyfill (localhost is a secure context; port is irrelevant). **Corrected by verification:** secure context is necessary but not sufficient — Firefox and Safari require transient activation, Chromium requires either `clipboard-write` permission or transient activation *and* a focused document (Chromium issue 40836365, `NotAllowedError: Document is not focused`). A literal copy button satisfies all of this; the failure mode is a handler that awaits something (a fetch, a `confirm()`) before calling `writeText`. Also imprecise: MDN's "available across browsers since March 2020" is the *newly*-available Baseline date; *widely* available is 30 months later (~Sept 2022). And Firefox only began treating `http://localhost` as trustworthy in Firefox 84, so the two halves of the claim were never simultaneously true on the cited date.

67. The teach-lesson zero-JavaScript ruling (core#379, 2026-08-04) is fatal to any in-lesson variant of every executing mechanism here and cannot be worked around — JupyterLite is client-side JS + WASM in a Web Worker plus a Service Worker; the code-cell strip is JS. Any in-lesson execution story must be a NEW surface (its own page, or an iframe in the drill client), never executable cells inside an existing teach-lesson snapshot.

## Refuted or corrected

Six of the fifteen adversarially verified claims were refuted; several more were amended. In severity order for #459:

1. **"Outbound HTTPS to the Anthropic API from in-browser Python is possible" — overstated in the way that matters most.** True for `/v1/messages`, false for `/v1/messages/batches`, which returns HTTP 400 `Disallowed CORS origin` at preflight from every one of five origins tested including `http://localhost:8631`. Batches is one of the six topics #457 says the labs must teach. **Why it matters:** it converts a footnote into a per-mechanism line item — any in-browser mechanism needs a mock, a fixture, or a local proxy for one-sixth of the curriculum, and that cost belongs in the #459 comparison rather than being discovered during build. The finding is empirical only with no first-party documentation, so it carries no stability guarantee either.

2. **The stock Anthropic Python SDK cannot reach the API from Pyodide at all.** The claimed `AuthenticationError: 401` is not reachable with a default client — you get `APIConnectionError: Connection error.` because the SDK's retry loop swallows the CORS failure. A genuine 401 requires `default_headers={"anthropic-dangerous-direct-browser-access": "true"}`, which the Python SDK never sets (zero grep hits in the 0.122.0 wheel). **Why it matters:** it means a Pyodide lab cannot run copy-pasted idiomatic SDK code. The scaffold must inject a non-default header, so what the learner practises diverges from what the exam tests — and the header Anthropic itself names "dangerous" becomes a permanent fixture of every Python lab.

3. **"The header is the sole gate" is wrong at three layers.** It keys on header *presence*, not the value `true` (sending `"false"` still passes CORS). The TypeScript SDK adds a second, earlier gate that throws client-side before any request, so setting the header via `defaultHeaders` does not help. And "no proxy-free path without it" is falsified as a universal — a cross-origin POST to Bedrock's `invoke` endpoint with no Anthropic header returned a readable 403 with valid CORS headers. **Why it matters:** the first two points change what lab scaffolds must contain; the third is a technical counterexample only — Bedrock is a different API surface that teaches none of the six required topics, so the claim should simply be scoped to `api.anthropic.com` rather than treated as opening a door.

4. **The diagnostic string for a CORS block is `TypeError: Failed to fetch`, not `AbortError: Failed to fetch`.** That combination is not one Chromium emits; the cited measurement almost certainly captured a harness timeout wrapper. 5/5 independent reproductions gave `TypeError`. **Why it matters:** if #459 or any lab-authoring guidance uses "AbortError" as the signature for "CORS blocked", it will mis-classify real timeouts as CORS failures and vice versa.

5. **The 377 KB single-file CodeMirror bundle has no syntax highlighting, and adding it breaks the single-file property.** Measured: zero token spans, line content is literal unstyled text. `@codemirror/lang-javascript` (+359 KB) and `@codemirror/lang-python` (+314 KB) both import esm.sh's absolute `/node/process.mjs`, which 404s when self-hosted — so self-hosting them requires vendoring an extra shim and rewriting specifiers, or adding an import map. **Why it matters:** the headline "377 KB, one file, no bundler, no import map" is the most quotable number in the whole survey and it describes a configuration the labs cannot actually use. The honest number for a JS+Python editor is ~1.05 MB across at least four files.

6. **CodeMirror's own bundle-size figures are four years stale, and its "you'll want to do classical bundling" guidance is five years stale and contradicted by its own current practice.** Reproducing the docs' exact recipe today gives 12–26% larger numbers across the board. And the bundler paragraph dates to 2021-01-05 — two months before Chrome shipped import maps — while CodeMirror's own `/try` sandbox has, since 2026-04-21, loaded unbundled per-package ESM via a generated 161-entry import map. **Why it matters:** the survey cited the doc's guidance as evidence that a bundler is required; the correct residue is narrower (an npm→browser *resolution* step is required; a bundler is not), and the sizes used in any #459 comparison must be the measured ones.

7. **Rustlings does not re-verify in a predetermined order.** Bulk re-verification checks *all* exercises in parallel across `available_parallelism()` threads with work pulled off an atomic counter — order-nondeterministic — and is not part of the watch loop at all. The state file also lives in the project root, not the exercise directory. **Why it matters:** low-stakes for #459 (rustlings is Rust-only and would need a toolchain this machine lacks), but if anyone copies the state-file design they should copy the real one.

8. **The full Pyodide distribution is *not* "far below GitHub's hard caps".** At 414,666,750 bytes it is 3.95x over the 100 MiB per-file block and cannot be committed to git at all — it is release-asset-only. Only pyodide-core (6.76 MB compressed) clears the caps. The CDN half of that claim was also measured against v0.28.3, ~11 months stale, and the current v314.0.4 runtime is 11% larger with `pyodide.asm.js` now a 404 (replaced by `.mjs`). **Why it matters:** anyone reading the original could conclude vendoring the full distribution is within caps. It is not, and a loader wired from the 0.28.3 filenames would 404.

9. **`ui-gate.sh` does not "match import syntax, not network fetches".** Two of its four patterns are bare substrings that match in URLs and prose: a `@carbon/` CDN `<script src>` fails the gate, and so does the sentence "This lab intentionally avoids carbon-components styling." Verified by running the exact regex against constructed cases. **Why it matters:** the reasoning that CDN-loaded lab pages are invisible to the gate does not hold, so the "just load it from a CDN" escape hatch is narrower than described. The much larger finding — that *any* file outside `engine/` and `scripts/` passes unconditionally, and that no CI step anywhere detects a `package.json`, lockfile, or `node_modules` — stands and is stronger than the original framing.

10. **`POST /api/<exam>/lab-result` would not be in-pattern.** The action segment regex is `[a-z]+` — no hyphens, no digits. `lab-result` 404s at the regex; the endpoint must be a single lowercase word or `server.mjs:174` changes too. Minor, but it was offered as evidence that ingestion is a trivial in-pattern addition.

11. **Amendments that did not overturn a claim.** Exercism's `tests` array is not unconditionally required at version 2+ (not required when `status` is `error`), and `test_code` is required only for Concept Exercises. `navigator.clipboard.writeText()` needs transient activation and (in Chromium) a focused document, not merely a secure context. Anthropic's `httpx` under Pyodide is a *fork* (`hoodmane/httpx` pinned in pyodide-recipes) whose version string makes it indistinguishable from upstream 0.28.1. The `codemirror@6.0.2` gzip figure is ~121,376 B headerless, not 121,382. The client is 490 lines, not 446.

## Coverage gaps (honest limits of this ONE cycle)

**Timings — the whole survey is nearly blind here.** No cold-start figure exists for any mechanism. The one JupyterLite first-cell number (3,011 ms) was measured with a **warm HTTP cache** and the cache could not be cleared, so the true cold number is unknown and must additionally carry ~13.9 MB of transfer at unknown link speed. No JupyterLite build was ever run, so there is no measured on-disk size for a built site and no build time. JupyterLab in the sibling repo was never started, so the 0.68 s uv / 0.08 s `node --test` terminal loop has nothing to be compared against. CodeMirror's runtime cost (parse/eval of the 377 KB module, memory, typing latency) was never measured — only that it mounts. Any latency number in #459 must be measured locally, not cited from here.

**The single biggest unmeasured number:** whether the 6.44 MB `pyodide-core` tarball is sufficient for the JupyterLite kernel, or whether self-hosting requires the ~395 MB full distribution. The kernel needs micropip and ipython wheels that core may not carry. This determines the entire offline/vendoring cost of the WASM-Python option and it is unresolved.

**Nothing was executed locally in the Pyodide angle by design.** Downloading and running third-party artifacts needs explicit user permission a non-interactive session cannot obtain, so all Pyodide numbers come from already-public hosted deployments and package metadata. Related: the local-origin behaviour is entirely untested — everything was measured at `https://jupyterlite.github.io` over TLS, never from `http://localhost:8631` served by `node:http`, so whether the Service Worker registers over plain http-on-localhost (it should; localhost is a secure context) and whether cca-prep would need to emit COOP/COEP headers are both open.

**Browser coverage is one browser.** All Pyodide measurements are Chrome 151 on macOS; all sandbox measurements are Chromium 148 / Electron 42.7.0. Safari and Firefox are untested throughout. JupyterLite claims support only for "the latest Chrome and Firefox"; Safari's status is not stated anywhere. The iframe main-thread-starvation result in particular is a **single measurement in one browser** using a same-site `srcdoc` frame that shares the parent's process — a genuinely cross-origin sandboxed iframe would be site-isolated and may not block the parent at all. Do not generalise it to "iframes always hang the page".

**Streaming and Batches were not exercised for real.** urllib3's `preload_content=False` returned data on a non-cross-origin-isolated page, but "buffered then read" could not be distinguished from genuine incremental delivery, and Anthropic SSE (`stream=True`) was never tested — that needs a real API key. Batches was only probed at the CORS layer; the full submit → poll → results-JSONL flow (which may redirect to a different host, and redirect handling in Emscripten urllib3 is explicitly "determined by runtime") is unverified end to end anywhere.

**Mock fidelity is proven for exactly one shape.** The `node:http` mock was verified against a single `tool_use` message response. It was **not** verified for SSE streaming, the Batches submit/poll/`results_url` `.jsonl` flow, or SDK-level retry/error-class behaviour — which is precisely where the "validation-retry loop" and `isRetryable` lessons live. If those exercises need faithful error semantics, the mock's cost is larger than one experiment suggests.

**The Python half of the code-cell-strip angle does not exist.** Nothing in that angle executes Python. A JS-only code-cell strip covers at most half the stated lab surface, and closing the gap means Pyodide (a separate, far larger payload) — which was not investigated from within that angle.

**The correct multi-package no-bundler CodeMirror load was never built.** Only the single pre-bundled entry was proven to work standalone. The deduped import-map route (core + JS mode + Python mode + linting, one shared `@codemirror/state`) is documented as fragile, and CodeMirror's own `/try` shows it working — but it was never built and run here, and no unbundled total transfer size or cold-load time was measured. The import-map path gets no tree-shaking, so the doc's gzipped figures do not apply to it.

**Operator ergonomics is entirely unmeasured and probably unmeasurable from here.** No study, benchmark, or number was found comparing time-to-first-exercise, task-completion, or drop-off for CLI-driven runners versus in-browser execution. The only hard ergonomics numbers in this document are machine latencies, not human ones. Worse, the available prior art optimises for a different problem: Exercism, rustlings, and NodeSchool all solve "get a stranger productive at scale"; cca-prep solves "keep one known person calibrated". That transfer assumption is unvalidated.

**The local-web-UI hop has no prior art that could be found.** This is absence of evidence from a search scoped to developer-education runners, not proof of absence. Its practical consequence is that the instructions-and-progress integration is design work with no template to copy, making it the least-well-estimated cost in the entire survey.

**Exercise authoring cost is entirely outside this survey.** How scaffold files get written — by hand, by the existing cca-prep generation pipeline, or seeded from exam-guide task statements — was never established, and it could dominate the mechanism cost it was compared against.

**Third-party embed facts could not be verified first-hand.** `codesandbox.io/docs` returned HTTP 403 (the embed-not-editable claim and the 400-credits / 20-sandboxes figures are search-engine summaries). `exercism.org` returned 403 (worked around via the first-party GitHub repos, but the rendered site was never diffed). WebContainer commercial licence pricing is a contact form. Codespaces iframe-embeddability was never checked at all, and the core-hours-vs-clock-hours question — which halves or doesn't halve the free allowance — could not be resolved from first-party docs. The Replit deprecation notice says "After August 1st" with no year on the page, and the current 2026 state was not checked.

**Adjacent options never evaluated:** Sandpack (CodeSandbox's embeddable component — almost certainly React-based, colliding with the ui-gate), Skulpt-style Python-subset interpreters (used by Runestone's ActiveCode; a reimplementation, so third-party SDKs are unlikely to work), and whether msw's service-worker interception can work without a bundler.

**Two mechanical unknowns about the host:** whether `engine/server.mjs` needs changes to serve a `vendor/` directory with correct MIME types for `.mjs` was never checked (finding 1 suggests yes, since there is no MIME map at all), and the real-world effect of a ~9 MB blob on CI wall-clock (`actions/checkout` fetch time) was never benchmarked.

**No education research on output-checksum self-check.** Hashing stdout and comparing against a published digest has engineering precedent but zero located studies of its learning effect, and none on expected-output-reveal timing.

**Adoption numbers are one-sided.** pypistats rate-limited after the `llm-mock` query, so there are download counts for the unadopted package (132/month) and none for vcrpy or respx to compare against. And no publicly redistributable corpus of real Anthropic `tool_use` / batches / `stop_reason` transcripts was found; `claude-cookbooks` notebooks carry outputs but their licence and replay-completeness were never audited.

**One timing inconsistency worth flagging as a data-integrity note:** anthropic 0.122.0 was uploaded to PyPI at 2026-08-13T18:36Z. Any measurement claiming to have observed 0.122.0 on 2026-08-12 — the survey's stated verification date — could not have done so.

## Open questions (candidate inputs to the #459 grill)

1. Is a lab that cannot exercise the Batches API against the live service acceptable, given Batches is one of the six required topics? If yes, does the mock/fixture that covers it also become the mechanism for the other five — and if so, does live-API capability still carry any weight in the choice?

2. Is putting the operator's `ANTHROPIC_API_KEY` into browser-reachable code — persisted to IndexedDB in the JupyterLite case — an acceptable posture for a single-operator offline tool, knowing Anthropic's own SDK names the enabling flag "dangerous" and the raw header has no first-party prose documentation?

3. Do the labs need to teach *idiomatic SDK code*, or is teaching the wire format acceptable? This is the fork in the road: idiomatic Python-in-browser requires injecting a non-default header the exam will never mention; idiomatic TypeScript requires `@anthropic-ai/sdk` and therefore a `package.json` in the repo; wire-format-only runs on Node built-ins and `uv` with nothing deposited anywhere.

4. Does "zero dependencies" in CLAUDE.md mean *no package manager* or *no third-party bytes*? A vendored 377 KB CodeMirror file, a vendored 13.5 MB Pyodide runtime, and a `uv`-cached wheel set outside the repo are three very different answers, and #456 currently distinguishes none of them. (Note: nothing in CI enforces any reading today.)

5. Is an author-time Python build step (`jupyterlite-core` + `jupyterlite-pyodide-kernel`) acceptable in a repo that has no build step and no Python at all? This is orthogonal to #456 — relaxing the npm rule does not help, because JupyterLite's artifacts are produced by a Python CLI, not installed from npm.

6. Given the unresolved git-history purge blocking the public flip, is committing any multi-megabyte binary before that flip acceptable — knowing GitHub retains PR head refs server-side so it stays fetchable without a Support ticket?

7. Does grading need to identify *which* judgment gap was missed, or is pass/fail per exercise enough? Per-assertion structure is what feeds telemetry-driven retirement, and it constrains the mechanism: only the code-cell strip (AST + intercepted fetch) and the Exercism-style file contract were shown to produce it.

8. Should lab results reach the drill app at all in slice one, or is a terminal-only loop with the app serving instructions sufficient? The file-contract half has a documented template; the app-ingestion half has no prior art found and is the least-estimated cost in this survey.

9. Is a JS/TS-only lab surface acceptable for slice one, deferring Python? The code-cell strip covers TS well and Python not at all; the terminal template covers both; JupyterLite covers Python well and TS barely (its JavaScript kernel's last release was 2024-03-26).

10. Does the lab surface need to survive being opened in Safari or Firefox, or is Chrome-only acceptable for a single-operator tool? JupyterLite documents support for "the latest Chrome and Firefox" only; WebContainers embedding is effectively Chromium-only; every measurement in this cycle is Chromium.

11. Is a mechanism that requires a network account or vendor ToS compliance (StackBlitz's paying-customer embedding restriction, Replit's read-only deprecation, Codespaces' account requirement) in scope at all for an offline localhost tool — or does that eliminate the hosted-embed column outright?

12. Should the lab live as a new route in `server.mjs` or as another view inside the existing self-contained `engine/public/index.html`? The second requires no server change whatsoever; the first requires a route, an explicit content-type per asset (there is no MIME map), and — if a result-ingestion endpoint is wanted — a change to the `[a-z]+` action regex.

13. Given that no CI step detects a `package.json`, lockfile, or `node_modules` anywhere in the tree, should #459's outcome be accompanied by a gate that actually enforces whatever #456 decides — or is prose enforcement in CLAUDE.md the intended posture?

14. What is the acceptable cold-start budget for a lab session? Nobody knows what any mechanism actually costs cold; if this matters, it needs measuring before the decision rather than after.

15. Given that the strongest efficacy evidence for in-place execution is vendor-authored and confounded, and the strongest evidence for non-executing check (Parsons) says it matches execution in less time — is "the operator can execute code in the page" a requirement, or a preference that the evidence does not currently support?
