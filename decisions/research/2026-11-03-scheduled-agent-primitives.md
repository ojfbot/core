# Scheduled-agent primitives for fleet-runner

Research draft for review, 2026-11-03.

This draft supports [What a scheduled-agent primitive gives you, generic vs vendor-specific (#308)](https://github.com/ojfbot/core/issues/308) in the [Fleet-runner map (#307)](../wayfinder/control-plane-conductor.md). The inspected core baseline is `b2459fa31d389516cd3c5f8d711251fdfd70d35e`.

This source review compares the incumbent launchd and GitHub Actions rails with Claude Code cloud scheduled tasks, formerly Routines. It revisits the trigger assumption in the [July loop engineering audit](../../docs/audits/LOOP-ENGINEERING-CROSSCHECK-2026-07-09.md). Evidence comes from current first-party documentation and the installed `launchd.plist(5)` manual on Yojimbo, macOS 27.0.1. Live scheduling, sleep behavior and account settings remain untested.

## Candidate input to the portability seam

A trigger submits a scoped intent or wakes the service. It can attach a provider receipt. The service records the intended occurrence, observed delivery, admission decision, attempt, and accepted result as separate facts. An expected occurrence with no delivery is distinct from an admitted job with no attempt. Use a stable occurrence key across trigger adapters and link duplicate submissions to the same disposition.

The worker connection is on the execution side of this seam. The resident worker opens a duplex connection, reports qualified capacity and can decline a slot request. Fleet-runner grants the attempt lease and owns the accepted result. A connected worker, an available slot, an accepted offer and a live lease are distinct states. Capture their evidence separately.

For the portability check, deliver the same synthetic occurrence through two controlled trigger paths, including a duplicate and an absent tick. Verify one service-owned admission and distinguish delayed or missing delivery from execution failure in the exported evidence. [The portability seam (#311)](https://github.com/ojfbot/core/issues/311)
