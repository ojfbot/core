Keep or cut

Lesson 0001 · prompt-ablation · for sorting instructions you wrote yourself

Every write-up of Boris Cherny's talk reports the same headline: 80% of Claude Code's system prompt deleted, and the model came out more intelligent without it. It's a good headline and it points the wrong way, because it invites one question — is my prompt too long? — when there are two, and only one of them is settled by deleting things.

Anthropic's team file is around 2.5k. Yours is roughly triple that in aggregate. Hold the alarm, though — that comparison is the trap this lesson is about.

The qualifier the coverage dropped

The primary source carries something the summaries cut. Yes, the model tests a little more intelligent without the prompts — and some prompts are kept anyway, because they help with product usability and the behavior you actually want when people use the thing. (transcript)

That splits every instruction you have ever written into two piles:

  1. Deficiency patches. Written because a model got something wrong. "Always check whether the file exists first." "Don't invent APIs." These are compensation, and a model upgrade turns them into dead weight — worse, into noise competing with the instructions that still matter. This is what the 80% was.
  2. House rules. What you want, which no model upgrade will ever supply on its own. pnpm and never npm. Grill before non-trivial work. Log deviations as you hit them. Never write northstar current: from a slice session. No amount of model intelligence produces these, because they aren't facts about competence — they're facts about your house.

The test that separates them: would a smarter model make this line unnecessary? If yes, it's a patch. If a smarter model would still need to be told, it's a rule.

Now look at your 7,350 tokens again. The pnpm rule, the grill posture, the deviation ledger, the movement-contract discipline — those are category two, nearly all of it. Boris's argument does not touch them. What it does target is anything you wrote to compensate for a model that no longer needs compensating, and you genuinely do not know how much of that you have, because nobody audits for it.

The method, when sorting isn't obvious

For the ambiguous lines, he doesn't argue — he ablates. The loop, from his own account: (transcript)

  1. Delete the entire system prompt
  2. Bring it back line by line, to find each line's individual impact
  3. Use evals to assess what each restored piece contributes
  4. Restore only what the model repeatedly stumbles on

Run every time a new model ships, across prompts, tools, and the harness code itself. Two knobs exist for it: a --system-prompt override, and CLAUDE_CODE_SIMPLE=1, which strips all system prompts including the ones buried inside tools.

Notice step 4's bar. Not "the model did fine without it" — repeatedly stumbles. Ablation is biased toward deletion by construction, and one good run is not evidence a line was useless.

And notice step 3, which is where copying this gets expensive. Anthropic has evals. Without them, "the model seemed fine" is a sample of one against a task you chose after forming an opinion. Your merge-quiz heatmap is the closest instrument you own, and it has zero cells. So the honest version here is: ablation sorts the ambiguous lines, and it needs something to measure against before its verdicts mean much.

1. Which line in a CLAUDE.md is the best deletion candidate?

The read-before-edit line. It's a deficiency patch — written because some model guessed at file contents, and a model that no longer does makes it dead weight. The other three are house rules: no upgrade tells a model you prefer pnpm, or that your ledger lives in that file, or what your movement contract is. Ask the diagnostic — would a smarter model make this unnecessary? — and only one of the four says yes.

2. Your ablation removes a line and the next run goes fine. What follows?

Almost nothing follows. Restoration is triggered by repeated stumbling, which means a single clean run is exactly the evidence the method expects to see even for lines worth keeping. The method leans toward deletion on purpose; that bias is only safe when something measures the downside. Option C is the opposite failure — "any doubt keeps it" is how 7,350 tokens accumulate in the first place.

3. What is the real obstacle to running this on your fleet tomorrow?

The missing measurement. Step 3 of the loop is "use evals," and that is the step you cannot currently perform — the comprehension heatmap has zero cells and nothing else scores instruction quality. The override knobs exist (--system-prompt, CLAUDE_CODE_SIMPLE=1), file size is a nuisance rather than a blocker, and the split across files is bookkeeping. Without a ruler, ablation still sorts the obvious lines — it just can't settle the ambiguous ones, which are the only reason you'd run it.

What this actually licenses

Not a cut. A sort — and a sharper question than the one the headline hands you.

You are not carrying 7,350 tokens of bloat. You are carrying an unknown mixture of house rules that should stay and deficiency patches nobody has audited since the models that motivated them. The mixture is the finding. Anyone who reads "80% cut" and reaches for their own file is answering a question about length when the real one is about kind.

Going deeper

One source: the transcript — specifically the qualifier about keeping prompts for product behavior, which every secondary write-up drops. That single clause is the difference between this being a sorting rule and a license to delete.

Worth asking next: which of your instructions were written against a model you no longer run? The pnpm rule has a date and a reason. Do the others? And a harder one — if step 3 needs an eval you don't have, is building that ruler the actual prerequisite here, ahead of the skill hardening already in flight?
