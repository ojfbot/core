Search by what you know

Built-in tool sequencing for CCAR-F task 2.5 · Lesson 0002 · 2026-08-12

You already know what every built-in tool does. Your three task-2.5 misses were never about identity — they were about order: which move goes first, and what follows it.Record 0002, misconception cluster 2: “tool identity is fine; the misses are on ordering and enumeration.” This lesson is one idea and two doctrines. The idea:

Search by what you know, then follow the graph. Never bulk-read.

Every canon answer on this task starts from the most specific thing the scenario already gives you — a string, a naming pattern, a file — spends the cheapest tool that can use it, and then follows what that step reveals. Every trap answer skips the identifying step and reaches for bulk: read everything, glob everything, batch everything.

Selection: match the tool to what you hold

The Bash row is a boundary, not a shortcut: when a built-in fits, the built-in is the canon answer — it is structured and permission-scoped, where shelling out to grep or cat is neither. Bash earns its place only when the job is execution.

Doctrine one: incremental exploration

Scenario shape: “understand how X works in this unfamiliar codebase.”

Canon sequence: Grep to find the entry points, then Read to follow imports and trace flows — building understanding incrementally, “rather than reading all files upfront.”Guide p.12, Skills in, fourth bullet — quoted almost verbatim. This bullet alone answers most 2.5 exploration stems.

Your H45 hand went to Glob-plus-batch-read: collect the files, read them in bulk, assemble the picture. That feels thorough and it is the flagged anti-pattern — it spends context on files the trace would never have visited, and it produces coverage, not understanding. The canon move always earns the next Read from the previous result.

Doctrine two: wrapper tracing

Scenario shape: “find how the helpers behind this wrapper/barrel module are used across the codebase.”

Canon sequence: first identify all exported names, then search for each name across the codebase.Guide p.12, Skills in, fifth bullet — the enumerate-then-search order is the whole point. Read the wrapper once to enumerate; Grep once per name.

Your H44 hand grepped the wrapper’s file path. That finds the files that import the module — and misses every call site, because consumers use the names, and names travel through re-exports and aliases the path search never sees. Enumeration first is not ceremony; it is what makes the search find usage instead of plumbing.

The pressure tell

Both misses share a signature: under closest-plausible distractors, the hand picks the direct bulk move where canon wants the enumerated incremental one. When two options both sound workable, ask: which one starts from something I already hold, and lets each step choose the next? If an option reads all/most files before it knows which matter, it is the trap — however efficient it sounds.

Retrieval — five scenarios

1. You are dropped into an unfamiliar 200-file service and asked how request authentication works. The canon first sequence?

Answer: Grep entry points, then Read to follow imports. The guide's incremental-exploration bullet verbatim: start with Grep to find entry points, then use Read to follow imports and trace flows, “rather than reading all files upfront.” Options 1, 3, and 4 are three costumes on the same bulk-read trap — Glob-batch was your H45 pick. Each Read must be earned by the previous result.

2. A barrel module utils/index.ts re-exports fourteen helpers. You need every place those helpers are actually used. First move?

Answer: enumerate the exports, then search each name. The guide's wrapper-tracing bullet: identify all exported names first, then search for each across the codebase. Option 1 was your H44 pick — path search finds importers of the module, not call sites of the names, and misses usage through re-exports and aliases entirely.

3. Edit keeps failing on a change because the anchor text appears in four places in the file. Canon fallback?

Answer: Read + Write. The guide names this exact fallback: “when Edit fails due to non-unique text matches, using Read + Write as a fallback for reliable file modifications.” Extending the anchor (option 3) often works in practice, but the stem asks for canon — and sed-via-Bash trades a structured, reviewable edit for an unscoped shell mutation.

4. Two jobs: (a) list every file matching **/*.test.tsx; (b) find which tests reference createSession. Canon pairing?

Answer: Glob for names, Grep for contents. The cleanest selection split in the guide: Glob matches file paths (**/*.test.tsx is its own example); Grep matches file contents (function names are its example). One tool per kind of knowledge you hold — and neither job is execution, so Bash never enters.

5. You must find every file importing a deprecated module, migrate each import, and confirm the suite still passes. Canon tool sequence?

Answer: Grep → Edit → Bash. Each tool where it is strongest: Grep because an import statement is a content string (the guide’s own Grep example); Edit for targeted modification; Bash only for the one genuine execution step. The distractors each smuggle Bash into a job a built-in owns (search in 1, mutation in 4) or bulk-read their way to the hits (3) — the same pressure tell as always.
